# openmicrokbd

## openmicrokbd/app — map for the deck host design (checked 2026-09-18; repo HEAD a668e11 "app 0.15.0", 2026-09-08)

### 1. Architecture: single-process GPUI app, NO daemon/client split
- `openmicro-app` 0.15.0 (`app/Cargo.toml`) is one binary. `app/src/main.rs:3-8`: `status_ipc::run_cli_if_requested()` first (CLI helper modes), else `gpui_app::run()`. The GUI process itself owns the HID handle, hotkeys, tray, IPC listener, release checks. There is nothing in openmicrokbd that resembles "service + GUI client"; the only IPC is an inbound, fire-and-forget event sink (below). The current openwalkietalkie `host/` (icon sync) is the opposite extreme: headless launchd agent, no IPC at all.
- Live module tree (`app/src/lib.rs:1-23`): actions, agent_integrations, behaviors, boot, config, device, dfuse, editor_logic, events, gpui_app, gpui_controls, host_state, i18n, intercept, keycodes, lucide, macos_updater, menubar, pixel, release, simple_icons, status, status_ipc. `app/src/app.rs` (6001 lines, makepad GUI) and `app_picker.rs` are orphaned — not declared in lib.rs, no makepad dependency in Cargo.toml. Live Rust ≈ 26k lines; `gpui_app.rs` alone is 6267.
- Data flow (the pattern to copy): background services → `events::post(AppEvent)` on a process-global `async_channel::unbounded` (`events.rs:33-59`; `AppEvent` = Device | Update | Release | Hotkey | Menubar | OpenSettings | Activity, lines 21-29) → single consumer `cx.spawn` loop in GPUI (`gpui_app.rs:1121-1133`) → framework-neutral reducer `HostState::handle_event(AppEvent) -> Vec<HostEffect>` (`host_state.rs:495-507`; `HostEffect` = ShowWindow | OpenSettings | Quit | ReleaseCellAfter | ExpireActivityAfter, lines 72-88) → `apply_host_effects` schedules timers/UI (`gpui_app.rs:1239-1280`). UI→device goes through `HostState.device_tx: Option<mpsc::Sender<DeviceCmd>>` (`host_state.rs:106`, `sync_device` 370-386).
- `HostState::new()` starts all services on the UI thread (required by tray-icon/global-hotkey on macOS) `host_state.rs:157-199`; `HostState::detached(config)` (201-245) builds the model with no HID/network/tray/disk for tests and previews. `#[cfg(test)]` makes `new()` hermetic (163-168).

### 2. The existing IPC (status bridge) — `app/src/status_ipc.rs`
- Transport: per-user Unix socket `dirs::cache_dir()/OpenMicro/activity.sock` (macOS → `~/Library/Caches/OpenMicro/activity.sock`), dir chmod 0700, socket 0600, stale socket unlinked, listener thread `openmicro-activity-ipc` (109-171). Windows: loopback TCP on a random port + 32-byte random hex token written atomically to `activity.json` (173-224, 262-289).
- Wire: one JSON object per connection, ≤4096 bytes, 1 s read timeout: `{token?, session_id, turn_id?, status, begins_turn}` (`IpcMessage` 40-50) → `ActivityEvent` (30-38). No reply, no request/response, no subscriptions. Session ids are namespaced `codex:`/`claude-code:`/`grok:`/`octoscode:` (98-105, 515).
- Hook helper: `OpenMicro agent-hook <codex|claude-code|grok|octoscode>` reads the agent's JSON hook payload on stdin (≤16 MiB, 457-462), maps event names to 5 states Idle/Working/Attention/Success/Error (`status_for_hook` 305-349; e.g. UserPromptSubmit→Working, PermissionRequest→Attention, Stop→Success, SessionEnd→Idle, Claude `PreToolUse` with tool AskUserQuestion/Elicitation→Attention, `Notification` idle_prompt→Idle, StopFailure→Error), sets `begins_turn` only on UserPromptSubmit (495), prints `{}` for Codex Stop hooks (468-474). Manual: `OpenMicro status <state> [client:session]` (522-540). Turn guard in reducer: stale events from an older `turn_id` are dropped (`host_state.rs:659-672`); TTLs 4 s terminal / 30 min failsafe (40-41, 689-699); priority Attention>Error>Working>Success>Idle (`status.rs:23-31`).
- Hook config templates: `app/codex-hooks.example.json` (UserPromptSubmit, PermissionRequest, PostToolUse, Stop, SessionEnd; `timeout: 2`), `app/claude-code-hooks.example.json` (adds PreToolUse matcher `AskUserQuestion`, PostToolUseFailure, PermissionDenied, Elicitation, ElicitationResult, Notification matcher `idle_prompt|permission_prompt|elicitation_dialog`, StopFailure). Installer `agent_integrations.rs`: targets `$CODEX_HOME/hooks.json`, `$CLAUDE_CONFIG_DIR/settings.json`, `$XDG_CONFIG_HOME/opencode/plugins/openmicro.ts`, `~/.deepcode/settings.json`, `~/.grok/hooks/openmicro.json`, `~/.octos/profile-defaults.json` (125-146); uses `env::current_exe()`, refuses macOS AppTranslocation (113-123); staged atomic writes, unique backups, managed markers, conflict detection (265-760).

### 4. Device transport (USB vendor HID) — `device.rs`
- `hidapi 2.6.6` (vendor HID) + `rusb 0.9.4` vendored (ROM DFU only). Identities `1209:0001` and `303A:8360` (compat mode), selected by usage page `0xFF60` (44-51). 32-byte reports; hidapi needs a leading 0x00 report-id byte (730-739); reply echoes cmd byte; unsolicited events `[0x80, src, a, b]` may interleave with replies and are decoded/forwarded, never dropped (752-760, 781-800); acks are `[cmd, 0x01]` (764-770); timeouts 500 ms / 1500 ms for flash ops (145-147). Command table 87-107 (VERSION 0x01 … SET_MODE 0x11, ENTER_BOOT/BOOT_INFO from shared crate).
- Worker: one `HidApi` per process on a std thread, `mpsc::Receiver<DeviceCmd>` (305-318); loop = `wait_for_device` (800 ms search, still serving offline commands, 365-394) → `hello` (VERSION, GET_MODE, BOOT_INFO, keymap read → `DeviceMsg::Connected`, 525-554) → `session` (drain commands first, then `read_timeout(30 ms)` event pump, 2 s presence re-enumeration because hidapi may return Ok(0) forever after unplug, 558-721) → `Disconnected` → re-search or update path (339-361). `DeviceCmd` (254-303), `DeviceMsg` (151-188), `UpdateMsg` (242-251).
- Shared contract crate: `openmicro-layout` no_std path dependency used by fw/boot/app (`Cargo.toml:19`); bootloader client `boot.rs` is generic over a `Transport` trait so upload logic is tested against a scripted fake (1-40).
- openwalkietalkie's current host (`host/src/main.rs`) already does BLE HID via hidapi on macOS: filter `303a:8360` usage page `0xff00` (89), `api.set_open_exclusive(false)` so Codex desktop keeps its handle (144), zero-timeout drain to detect removal without BLE traffic (19-34), single instance via `flock` on `~/Library/Caches/OpenMicroDial/icon-sync.lock` (36-55), 500 ms poll, 60 s layout re-check; shares the protocol module with firmware via `#[path = "../../src/ui/icon_sync.rs"]` (3-5). Deck channel-5 rules (`docs/deck-protocol.md:10-33`): report id 6, `[6, 5, len, payload≤61]`, LF-terminated JSON ≤1024 B, ≤1 report/8 ms, ≤4 agent updates/s, other channels 2 (Codex RPC) / 3 (icon sync) / 4 (diagnostics) must be left alone.

### 7. What to reuse for the deck host
- Copy verbatim / near-verbatim: `events.rs` bus; `HostState`+`HostEffect` reducer with `detached()` test constructor; `status_ipc.rs` hook decoding (`status_for_hook`, namespaces, `begins_turn` turn guard, size caps, Codex `{}` stdout rule); `agent_integrations.rs` installer machinery; `pixel.rs`/`gpui_controls.rs` theme + `install_theme`; `menubar.rs`; `gpui_app.rs::run()` bootstrap, dock/hide handling, `on_app_quit`; `config.rs` load/save/`.invalid`/sanitize; `package-macos.sh` + `Info.plist.in` + `release.yml` + Sparkle bridge; device worker session shape (search → hello → session with command-first drain, paced reads, presence check) and the "events may interleave with replies" reader.
- Must be new: a bidirectional, multi-client API (the socket today is one-shot inbound JSON with no replies/subscriptions), BLE-HID pacing/framing for channel 5, the launchd service split (borrow `openmicrodial/tools/install-host.sh`), non-exclusive HID open coexisting with Codex desktop (`host/src/main.rs:144`), and a GUI client that receives state over the API instead of owning `device_tx`.

## Options
### Reuse verbatim: event bus + reducer + effects (events.rs, host_state.rs HostState/HostEffect/detached)
- pros: Proven framework-neutral core with 20 reducer tests; keeps GPUI code thin; detached() gives hermetic tests. Maps cleanly onto a daemon: the daemon runs the reducer, the GUI client renders a mirrored state.
- cons: Today the reducer owns device_tx and platform services (tray, hotkeys); for the daemon/client split those must be moved out or made pluggable.
- recommendation: Adopt; split into daemon-side reducer (device, agents, voice) and client-side view-model fed by API events.
### Reuse the status_ipc hook helper and agent_integrations installer as the agent-CLI ingress
- pros: Already handles Codex, Claude Code, Grok, Octoscode, OpenCode, Deep Code event vocabularies, turn guards, session namespacing, atomic config edits with backups, AppTranslocation refusal. Hook JSON templates exist for Codex and Claude Code.
- cons: One-directional: hooks cannot receive answers/orders. The deck needs a return path (e.g. PermissionRequest hook blocking on a daemon reply within the hook timeout, or agents polling the API). Gemini CLI is not covered.
- recommendation: Reuse the decoding/installer code; extend the hook helper to a request/response client of the new API with a bounded wait.
### Reuse the openmicrokbd Unix-socket convention for the daemon's open API
- pros: Path convention (dirs::cache_dir()/<App>/, 0700/0600), Windows token scheme, size caps and timeouts are already thought through.
- cons: The existing protocol is one JSON object per connection with no replies or subscriptions; it cannot serve a GUI client, voice pipeline, or third parties. Needs a real framed request/response + event-stream protocol.
- recommendation: Keep the path/permission conventions; design a new bidirectional protocol (line-delimited JSON-RPC over the socket, optionally also loopback WebSocket for non-Rust clients).
### Reuse the GPUI bootstrap, theming, tray and macOS window/dock handling for the new GUI client
- pros: gpui 0.2.2 + gpui-component 0.5.1 patterns are working and packaged; pixel.rs/gpui_controls.rs give an instant consistent look; menubar.rs and dock-policy code are drop-in.
- cons: gpui APIs move between releases (spawn closure signature, Menu/MenuItem); staying on =0.2.2 keeps the patterns valid but freezes the version. Tray must live in the GUI client (needs NSApp main loop), so tray-only mode requires the GUI process to run even when the daemon does the work.
- recommendation: Copy gpui_app::run(), pixel.rs, gpui_controls.rs, menubar.rs; keep the pinned versions initially.
### Reuse device.rs worker shape and openwalkietalkie host's non-exclusive hidapi BLE access for the deck transport
- pros: Search/hello/session/presence loop, interleaved-event reader and command-first draining are directly applicable; openwalkietalkie host already demonstrates coexisting with Codex desktop via set_open_exclusive(false) and zero-timeout removal detection.
- cons: Deck channel 5 needs 8 ms pacing, LF-framed multi-report JSON lines and channel demultiplexing that device.rs lacks; hidapi BLE behaviour on macOS (report sizes, disconnect semantics) differs from USB.
- recommendation: Write a new deck transport module modelled on device.rs, sharing src/deck/proto.rs with firmware via #[path] like host/src/main.rs does for icon_sync.rs.
### Reuse packaging/CI (package-macos.sh, Info.plist.in, release.yml, Sparkle) and openwalkietalkie's install-host.sh for launchd
- pros: Notarized, stapled, Sparkle-updated pipeline already fail-closed; launchd plist generation with KeepAlive/RunAtLoad and log paths exists in the sibling repo.
- cons: A daemon + app bundle needs a combined story (daemon inside the .app bundle, LaunchAgent pointing into it, Sparkle relaunch restarting the agent) that neither repo has.
- recommendation: Take both; add a LaunchAgent whose ProgramArguments point at a helper executable inside the app bundle.

- resources/NotoSansSC.ttf is bundled but unreferenced in the GPUI code — confirm it is dead weight before copying resources/.
