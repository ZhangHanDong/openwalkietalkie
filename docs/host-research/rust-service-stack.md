TRANSPORT DECISION (topic 1): Do BOTH listeners on one axum Router: (a) Unix domain socket at `~/Library/Application Support/OpenMicroDial/deckd.sock` (dir 0700; macOS sun_path is 104 bytes — SDK sys/un.h:79 — so keep paths short; Linux later: $XDG_RUNTIME_DIR/openwalkietalkie/deckd.sock) authenticated by peer credentials (tokio `UnixStream::peer_cred()` gives uid/gid and pid on macOS+Linux; axum's unix-domain-socket example shows `axum::serve(UnixListener, ...)` with `into_make_service_with_connect_info::<UdsConnectInfo>`); (b) `127.0.0.1:<port>` HTTP+WS for parties that cannot use a UDS: Claude Code `http` hooks, Codex/Gemini/Claude Code streamable-HTTP MCP clients, browsers/scripts. Auth for (b): random bearer token in a 0600 file next to the socket (`~/Library/Application Support/OpenMicroDial/token`), written by the daemon, read by clients (Tailscale's `sameuserproof-$port` and Syncthing's `X-API-Key` are the precedents); reject any request whose `Origin` header is present and not allowlisted (WebSocket handshakes are not covered by same-origin policy; the MCP spec also makes Origin validation a MUST with 403). Never bind 0.0.0.0. Port discovery: write `port` into the same 0600 dir (like Tailscale's `ipnport` symlink) so the GUI/CLI never guess. Protocol style: one JSON envelope used on both WS and UDS: request/response `{ "id", "method", "params" }` (JSON-RPC 2.0 framing is fine and lets rmcp-style tooling reuse it) plus server-push `{ "event", "rev", "data" }`; expose the same read-only state also as REST GET (`/v1/state`, `/v1/agents/{id}`) and an SSE stream (`axum::response::sse` with KeepAlive) for curl/scripts; write operations as POST. Version with `/v1` path prefix + `GET /v1/info {api_version, daemon_version, capabilities[]}`; additive-only field evolution (mirrors deck-protocol's "unknown fields ignored" rule, docs/deck-protocol.md:55). obs-websocket's `Hello→Identify(eventSubscriptions bitmask)→Identified` and `RequestBatch` are worth copying for the WS session (subscription filter + high-volume events opt-in, e.g. transcript deltas).

ChatGPT: MCP servers must be public HTTPS or use OpenAI's Secure MCP Tunnel (openai/tunnel-client, outbound long-poll HTTPS, developer mode); feasible but opt-in, keep out of v1. Maturity: rmcp 3.4.0 released 2026-09-15, active weekly cadence, 3.x migration guide, ~49% documented; spec 2026-07-28 removed sessions/GET streams/server-initiated requests (MRTR) and moved change notifications to `subscriptions/listen` — rmcp is dual-era, so older clients (2025-11-25 `initialize` + `Mcp-Session-Id`) still work.

CONFIG + EXTENSIONS (topic 4): `~/Library/Application Support/OpenMicroDial/config.toml` (macOS) / `$XDG_CONFIG_HOME/openwalkietalkie/config.toml` (Linux) via `directories::ProjectDirs`; sections `[api] port/bind/token_file`, `[device]`, `[agents.<name>] kind/slot`, `[macropad.<face>]` (the deck's `macro src` = dotfile name), `[voice]`, `[hooks]`. Hot reload with notify 8.2 + debouncer (two-read debounce like main.rs:167 today), validate whole file before `ArcSwap::store` (mirrors the device's "bad line changes nothing" rule), then emit `config.changed` on the bus. Persist device-authoritative state (`faces`, `set` values received from the device, deck-protocol.md:96-99) in a separate `state.json`, not in the user's TOML. Extension model: third parties are ordinary API clients (token + WS/UDS) — like Tailscale/Docker/Hyprland — plus optional user script hooks `[hooks.on_event] command = [...]` executed with the event JSON on stdin (Codex `notify` style), rate-limited and async. No in-process plugins in v1.

EVENT MODEL (topic 5): One `Store` (RwLock or actor) holding `Snapshot { rev: u64, agents: BTreeMap<AgentId, Agent>, cards, replies, focus, faces, settings, device: Link }`; every mutation is an idempotent upsert keyed by stable ids (agent slot 1..8, card (agent,id)) that bumps `rev` only if something changed, and appends an `Event { rev, kind, payload }` to a bounded ring (Syncthing's `/rest/events?since=` model: monotonic ids, slow clients detect a gap and refetch the snapshot). Fan-out: `tokio::sync::broadcast` (capacity power-of-two, `RecvError::Lagged(n)` → subscriber resyncs from `GET /v1/state`) for WS/SSE/UDS subscribers; `tokio::sync::watch<Snapshot>` for consumers that only need latest-state (device writer, menu-bar icon). Device writer task = the deck protocol's session state machine (hello every 5 s with sid; full sync then `synced` when device sid != ours; 15 s → offline; `up` handling) with a paced output queue: ≤1 report/8 ms, coalesce `agent` title updates to ≤4/s/agent (keep-latest per key), send `ws` only while an Omarchy face is visible (`face`/`hello.faces`), respect 1024-byte lines (deck-protocol.md:37-49, 72-104). Inbound device events (`key`, `ptt`, `answer`, `channel`, `snooze`, `set`, `faces`, `face`, `err`) become bus events and, where they change host truth, store mutations (echo `focus{ack:seq}` for `channel`).

## Options
### Transport A: HTTP+WebSocket on 127.0.0.1 only (bearer token file 0600 + Origin allowlist)
- pros: One listener serves every party: Claude Code http hooks, Codex/Gemini/Claude Code MCP clients (streamable HTTP needs HTTP anyway), gpui GUI, curl/scripts, browsers; trivial on Linux/Windows later; Tailscale's macOS design proves the token-file pattern.
- cons: Any local process (or any web page unless Origin is checked) can reach the port; token file must be created before clients start and rotated on daemon restart; no caller identity (uid/pid) for audit; port collisions need a discovery file.
- recommendation: Not alone.
### Transport B: Unix domain socket only (peer creds)
- pros: Kernel-enforced per-user access (dir 0700) + uid/gid/pid from `peer_cred()` for audit/authz; no token, no Origin issue; axum serves it natively; Docker/Tailscale/Hyprland precedent.
- cons: Claude Code `http` hooks and every MCP streamable-HTTP client need a TCP URL; sandboxed App Store GUI could not connect (Tailscale's reason for TCP); macOS 104-byte path limit; Windows later needs named pipes.
- recommendation: Not alone.
### Transport C (RECOMMENDED): both listeners on one axum Router — UDS (primary, peer-cred auth) + 127.0.0.1 HTTP/WS/SSE (token + Origin check) + `/mcp` streamable HTTP mounted from rmcp
- pros: Covers all parties with one codebase and one JSON contract; GUI and CLI use the UDS; agent CLIs use loopback; MCP spec's localhost+Origin+auth requirements satisfied; port and token discovered from files in the same 0700 dir.
- cons: Two auth paths to test; token/port files add install-time state; slightly more surface.
- recommendation: Adopt for v1.
### API style: JSON-RPC 2.0 envelope over WS/UDS + REST GET/SSE mirror (RECOMMENDED) vs pure REST+SSE vs jsonrpsee
- pros: JSON-RPC framing reuses what MCP/rmcp already speak (custom UDS transports SHOULD reuse stdio framing per the spec), supports batching and server push in one socket; REST GET + SSE keeps curl/scripts/dashboards trivial; schemars gives one JSON Schema for both. jsonrpsee 0.26 would give WS+HTTP+subscriptions out of the box but is a second web stack next to axum.
- cons: Custom JSON-RPC over axum WS means writing the dispatcher (small); jsonrpsee has slow release cadence (last stable 2025-08-11) and would not share the router with rmcp.
- recommendation: axum + hand-rolled JSON-RPC dispatcher generated from a serde enum; skip jsonrpsee.
### MCP exposure: in-process rmcp streamable HTTP at /mcp + `deckd mcp-stdio` shim packaged as .mcpb (RECOMMENDED) vs separate MCP server process
- pros: Same state store, no IPC hop, tools call the store directly; stdio shim satisfies Claude Desktop (stdio-only config, .mcpb binary type) and any legacy client; rmcp is dual-era so 2025-11-25 clients still work.
- cons: rmcp is pre-stable in spirit (weekly minor releases, ~49% docs); spec churn (2026-07-28 removed sessions/GET stream) means client compatibility must be tested per app; ChatGPT needs the OpenAI tunnel client — defer.
- recommendation: Adopt; treat ChatGPT as a post-v1 experiment.
### Process model: one workspace, two artifacts — `deckd` LaunchAgent binary with subcommands (run/status/hook/mcp-stdio/ctl/install) + `OpenWalkieTalkie.app` gpui client (RECOMMENDED) vs single binary that is also the GUI
- pros: Daemon survives GUI quit/crash and starts at login; GUI is an ordinary API client (Docker Desktop/Tailscale pattern); .app bundle gives Dock/menu bar, Info.plist usage strings, and a stable Developer-ID-signed identity for Microphone/Accessibility TCC; HID works from a headless LaunchAgent today (verified).
- cons: Two build/sign/install paths; gpui adds a heavyweight dependency (Metal, pre-1.0 API churn) and needs a tokio bridge (gpui_tokio pattern); a single binary would be simpler to ship but couples GUI lifecycle to the daemon and TCC prompts to a CLI-looking process.
- recommendation: Two artifacts; sign both with Developer ID before shipping (ad-hoc breaks TCC grants on rebuild).
### Config: TOML + directories + notify hot-reload + ArcSwap (RECOMMENDED) vs SQLite/JSON app state store
- pros: Human-editable dotfile (spec asks for power-user dotfile config); validated-then-swapped whole-file reload mirrors the device's atomic-line rule; Karabiner/Hammerspoon precedent.
- cons: notify 9.0 is still rc; editor save patterns need debouncing; device-authoritative state (faces/set) must live outside the user's file (state.json) to avoid clobbering edits.
- recommendation: Adopt; keep persisted device state in a separate JSON file.
### Event model: revisioned Snapshot + bounded event ring + tokio broadcast for subscribers + tokio watch for keep-latest consumers (device writer, tray) (RECOMMENDED) vs per-subscriber unbounded mpsc
- pros: Lagged subscribers resync from `GET /v1/state` (Syncthing model); idempotent upserts by stable ids make hook redelivery harmless; the device writer's pacing/coalescing (8 ms/report, 4 agent updates/s) is a natural keep-latest-per-key queue fed from watch.
- cons: Broadcast clones events per receiver; ring size tuning; needs explicit `rev` in every push so clients can detect gaps.
- recommendation: Adopt.
### Extension model: third parties as API clients + optional user script hooks (`[hooks.on_event] command=[...]`, event JSON on stdin) (RECOMMENDED) vs in-process plugin runtime (Lua/JS/WASM)
- pros: Zero plugin ABI; any language; matches Tailscale/Hyprland/obs-websocket; scripts mirror the Codex `notify` contract users already know.
- cons: No UI extension points; scripts run with user privileges (Gemini-style fingerprint warnings advisable); latency of process spawn (use async + rate limit).
- recommendation: Adopt for v1; revisit WASM plugins only if a real need appears.
